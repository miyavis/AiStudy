## 1 模型层原理（对应教程第 1 步）

### 1.1 大模型的本质：一台"预测下一个词"的概率机器

先建立一个不浪漫但准确的画面：**LLM 既不"理解"，也不"查询"，它在算条件概率**。

你给它一串 token，它输出的是一个巨大的概率分布——"下一个最可能是什么"。然后从中**采样**一个词，接着这个词被追加进输入，再算下一个……所有看起来连贯的长回答，都是这个"逐步采样"的过程滚出来的。

两个立刻能解释反直觉现象的推论，都源于此：

- **为什么上下文那么重要**：因为模型没有别的记忆源。它对"情况"的全部认知，就是这次发过去的 messages。没写进去的东西，就是不存在。
- **为什么它会一本正经地编造（幻觉）**：因为它是概率生成器，不是事实数据库。"编一个像样的答案"和"说出正确答案"，在它的机制里是同一件事——哪种概率高就采哪种。训练数据里出现频繁且格式完整的，就更容易被采出来。

采样本身有两个你知道名字的旋钮：

- **temperature**：把概率分布"拉平或削尖"。0 度≈永远取最高概率词（稳定、易复读），越高越随机（多样、易跑偏）。工具调用场景，我们其实希望稳定——所以有时设低温度反而工具调得准。
- **top_p（核采样）**：只在"累计概率达到 p 的那一小撮高概率词池"里采样，避免连长尾离谱词都参与。

### 1.2 token 与上下文窗口：模型的"工作内存"

**token** 不等于字/词，是训练时分词切出来的高频片段。一个关键实务：**中文每字消耗的 token 通常比英文单词更多**（英文很多常用词就是 1 个 token，中文一个字常是 1~2 个 token）。所以同样上下文窗口，中文能塞的内容比英文少。

**上下文窗口**是模型的全部"眼前世界"。qwen3 的窗口是有限的（数百 KB token 级），超了就装不下——这也是教程 1.2 观察点让你盯 prompt_tokens 累加曲线的原因：**不是模型"记性差"，是"工作台"就这么大**。

必须知道的性能事实——**为什么 agent 跑到后期每轮越来越慢**：模型在生成时，会把已有上下文的中间计算结果（KV cache）存起来加速。长上下文意味着：

1. 每秒生成(token/s)会被长上下文轻微拖慢；
2. 更狠的是**首 token 延迟**——每轮请求进来都要先处理全部历史，历史越长、第一步的时间越久。4070S 这种本地小卡上，agent loop 跑十几轮后那个"越来越卡"的感觉就是它。

（云端服务靠 **prefix caching**（对相同前缀复用已算好的 KV）大幅缓解，本地 Ollama 也做类似优化，所以"历史开头部分尽量保持不变"能省时间——把 system prompt 放最前、别让每轮请求的前缀重新洗牌，是免费的性能优化。）

### 1.3 三种角色为什么"权重不同"

system / user / assistant 的不对称不是魔法，而是**训练格式**：模型在后期微调时见过的数据里，system 永远在开头、代表"所有者指令"，且它几乎总是遵守。所以：

- system 放边界与规则（"不确定就说资料未提及"）有效，因为训练分布迎合它；
- 当 user 消息和 system 冲突时，多数模型仍倾向 system——**但不是铁律**，越小的模型越容易被 user 消息"带跑"。这是为什么教程里量本地模型"病得明显"——安全隐患要靠工程侧（收窄工具权限、输出校验）兜住，不能全指望模型自觉。

### 1.4 12GB 显存怎么装下 80 亿参数：量化直觉

神经网络的"参数"本质是一堆浮点数。逐资产算：

- qwen3 的 80 亿参数，每个用 **16 位浮点数（2 字节）**存 → 约 16GB；
- 但浮点数的"精度高位"对模型输出影响很小，把它们**压缩成 4 位整数（0.5 字节）**并把余下的尺度因子单独存 → 约 4~5GB。这就是你 pull 下来的 `q4_K_M` 这类量化格式。

代价是**有损**：一些权重细节被抹掉，模型会轻微变"愣"（偶尔选词更保守、复杂推理稍钝）。但实测 4 位量化对 7~14B 模型的日常对话/工具调用几乎无感——这也是整个本地推理生态能跑起来的一半原因（另一半是推理工程的 KV cache 之类显存优化）。

这个数字是可以从纸面参数推出来的：4070S 的显存带宽决定生成速度上限，8B Q4 权重约 5GB，生成一个 token 就要把全部权重过一遍带宽，4070S 带宽约几百 GB/s → 每秒能过权重几十遍，对应每秒 40~70 个 token——和你实测对得上。**不是玄学性能，是可以从参数纸面推出来的。**

## 2 Function Calling 原理（对应教程第 2 步）

### 2.1 工具调用不是"接了 API"，是"训练出来的习惯"

初学者最容易误会是：把 tools 数组传上去，模型就"拥有"了这个函数的执行能力。真相是——**执行自始至终只发生在你的 Python 里**，发生在模型里的只是一个行为：

训练阶段，模型见过大量"用户问事 → 模型吐出一段结构化 JSON 说请帮我调这个工具 → 结果回来 → 模型基于结果回答"的数据，于是模型的概率分布被**调教成：见到 tools 定义 + 检测到意图匹配时，会用特殊标记吐出一个 tool_calls 结构**。你收到的 tool_calls，本质还是采样出来的文本，只是格式被训练成了统一形状。

这个视角立刻解释三件事：

1. **为什么 tools 定义里的 description 是决定性的**——模型"选工具"的动作不是路由到某个服务，而是在上下文里做语义匹配：你的问题意图和哪段 description 最相似？（后面 4.2 会讲，这和 RAG 检索同构）
2. **为什么小模型会忘调工具**——工具列表长了、描述写得含糊，意图匹配就会输给"直接按常识回答"的概率。
3. **为什么多工具贪心时会调错的工具**——不是 bug，是概率误选。description 重写后概率就变了。

所以 **说透了：写工具描述 = 写 prompt。** 你在为一次"未来的语义匹配"布设路标。

### 2.2 tool_call_id 对账：一次迷你的"事务协议"

回传结果时必须带上 tool_call_id、服务端才收，这不是格式洁癖，而是一个**对账机制**。把整个流程看成一轮分布式系统的消息事务：

```text
client ──(消息+工具声明)──► model      请求
model  ──(tool_calls + id)──► client   记账式响应："我要求了这两笔调用"
client ──(结果, 引用 id)────► model    逐笔核销："这笔结果对应那次要求"
model  ──(自然语言回答)────► client    报销完成
```

模型每轮收到的 messages 变长时，服务端要校验"assistant 发起的每次调用都有一笔相引的结果"，缺一笔或 id 对不上就报错。**你在教程第 3 步会踩到的很多报错，都来自这套对账被破坏**（比如忘了把 assistant 的 tool_calls 消息写回历史）。

### 2.3 失败模式清单（本地小模型尤其常见）

| 失败模式 | 机理 | 对策 |
|---|---|---|
| 不调工具直接猜 | "常识回答"概率胜过"调工具"概率 | description 写强需求感（"必须查询…才能回答"）；system 里规定"涉及事实必须先调工具" |
| 参数幻觉（捏造日期、给错误枚举） | 模型没学过你的领域词汇，自由生成 | 把合法取值写进 description/枚举；或接收后校验并回传错误 |
| 坏 JSON（arguments 解析失败） | 采样被截断或格式漂移 | try/except 后把原始串和错误回传给模型重试 |
| 过度调用（明明能一步答完还连环调） | 小模型把"调工具"当成贪心奖励 | system 说"信息已足够时直接回答"；收窄工具集合 |
| 该并行却串行（先查 A 再查 B） | 多数模型一轮只稳定吐一个调用 | 接受它；多轮循环本来就能跑完 |

## 3 Agent Loop 原理（对应教程第 3 步）

### 3.1 ReAct：让"想一下、动一下"交错成形

教程第 3 步的 while 循环，学界名字叫 **ReAct（Reasoning + Acting，2022 年论文提出）**：让模型**在行动之间穿插推理**，而不是一次性规划全部步骤。你的 trace 输出（每轮打印"调用了什么"）就是在人工复现 ReAct 的观测。

在此之前，人们试过两种失败更多的方式：让模型一口气规划（大任务下中途走偏就全盘皆错），或让模型只输出行动不输出理由（错误率高且不可调试）。ReAct 的洞察在于**每一步的"理由"为下一步提供了地基**——你在教程里给 system prompt 写的"必须先思考再调工具"，就是在复刻这个机制。

### 3.2 为什么"一个 while 循环"能突然解决难题

这个问题的答案是最值得内化的原理。推理模型有这种能力，不是神奇，而是**把"一次到位"的低概率难题，拆成了一串"每步都简单"的高概率局部决策**：

- 一次性答"离下周三整还有多少小时"——小模型直接算大概率错；
- 分成"先调 get_now → 拿到周二 → 手算/调 calc 差值 → 汇报"这种粒度，**每一步都是模型稳赢的题**。

循环结构提供的，正是这个"错一步、改一步、再往下走"的修正空间。也解释了为什么 max_turns 这种"死循环收束"是必需的——概率机器没有内驱的"该停了"，只在每轮采样都给出自然语言结论时才停下；遇到失败信号时，它会倾向于再试一次，于是形成死循环。

### 3.3 报错回传为什么有效：把环境反馈接进概率

教程 3.3 强调"工具报错要回传给模型，不要自己 raise"。原理上它和 ReAct 是一个意思——**把环境的真实反馈（失败信号）纳入下一轮的条件概率**。模型看到 `{"error": "仅支持四则运算"}` 后，下一轮大概率会改参数或换工具。

反之，如果你在 agent 里静默吞掉错误、直接返回空字符串，模型就会在"信息已够"的错觉里继续编造答案。**agent 的韧性不是模型自带的，是你决定"错误要不要给模型看"的这一瞬间赋予的。**

### 3.4 agent vs workflow 的分水岭（对应结业清单）

Anthropic 在《Building Effective Agents》里给出的界线：**决定系统下一步动作的主体是谁**。

- 写死的行为链（代码 if/else 串工具）= **workflow**。可预测、低成本、行为稳定——多数生产系统该用这个。
- 模型在循环里自己决定下一步 = **agent**。灵活但贵、慢、难测。

实务直觉：**能用 workflow 部分解决的，就不要上 agent。** agent 适合"路径无法预知"的任务（开放式研究、多源信息聚合），不适合"步骤固定"的任务（每次都查天气再穿衣）。教程第 3 步的例子其实是"假 agent 需求"——真生产里这种固定流程更该写死。

## 4 Memory 与 RAG 原理（对应教程第 4 步）

### 4.1 记忆的分层模型：人类记忆的工程影子

教程里只做了 SQLite 存储，但值得看清它是整个"记忆体系"里最底的那一层。工程界通行的分层：

| 层 | 载体 | 内容 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 上下文窗口 | 当前对话全文 | 一次会话内 |
| 短期记忆 | 检索出的历史/摘要 | 本用户近期的偏好与事实 | 跨会话 |
| 长期知识 | 向量库/文档 | 领域资料 | 半永久 |

你的 04a 是第 1 层→第 2 层的单向写入；真正的生产记忆系统做的是**压缩与遗忘**：把几十轮对话摘要成几句事实（"用户叫张三，偏好简短回答"），存进去的是摘要不是原文。**"记性"从来不是存得好，而是扔得对。** SQLite 里那张表只是空间，策略才是记忆。

### 4.2 embedding 到底在算什么：语义坐标

教程 4.2 一步带过的"向量化"，是 RAG 的心脏，值得单独讲直觉。

把每个文本块映射为一个**高维向量**（bge-m3 是 1024 维）。训练这些模型的机制叫**对比学习**：喂百万级"这个句子和那个句子意思相近/不相近"的标注对，逼着网络学会把**语义相近的文本投到空间中相近的位置**。所以：

- "如何退货"和"退换货流程"在向量空间几乎贴在一起；
- "如何退货"和"今天天气不错"隔着半个空间。

**检索 = 在这个语义空间按方向找邻居**。余弦相似度公式的直觉：两个向量夹角越小（方向越一致，不管长短），句子语义越像。用长度比用长度差，是为了把"字数多"从相似性度量里剔除。

一个惊喜的融会贯通：**第 2 步的"模型选哪个工具调"，和第 4 步的"检索哪个文档块"，在向量层面是同构的**——都是在语义空间找最近邻居，只是一个是模型内部权重做的，一个是外置向量库做的。

### 4.3 为什么切块参数这么要命

RAG 的检索上限，早在切块那一刻就定死了。两个失败模式都要贴脸感受：

1. **块太小（比如 50 字）**：答案需要的上下文被腰斩。半句话被塞进向量，语义坐标本身就残缺，检索时和问题在空间里不爱挨着。
2. **块太大（比如 5000 字）**：一坨块里塞了五个主题，向量方向变成这五个主题的"平均质心"——问题只问其中一个主题时，这个"什么都沾"的向量反而排不进 top-k。同时大块还会稀释大模型注意力（上下文里塞一堆不相关的话）。

400~800 字 + 50~100 重叠是处理"一般文章"的经验甜点位。**但真正的答案永远是：先打印出 top-k 命中了什么，再调参。** 盲调切块参数和盲调学习率一样，是浪费时间的仪式。

### 4.4 RAG 的失败模式与诊断路径

| 症状 | 病根 | 对策 |
|---|---|---|
| 答"资料未提及"，但其实资料里有 | 检索没命中（切块/相似度错） | 打印 top-k，看正确的块排第几 |
| 答案张冠李戴（引用了错文档） | 命中了但 prompt 太弱 | 加强 system 约束；返回时带来源 |
| 答了但答案只覆盖一半 | top-k 太小 / 重叠不够 | 调大 k；增大块间重叠 |
| 中文检索明显比英文差 | 模型对语料领域不熟 | 换更对路的 embedding 模型；或混检 |
| 问题一写复杂就全崩 | embedding 只对短查询友好 | 先让 LLM 改写查询再检索（query rewriting） |

进阶方向一个节奏感清单，按性价比排：**混合检索**（BM25 关键词命中补上向量检索的"专有名词盲区"）→ **重排序**（先粗召回 50 个，再用交叉编码器精排）→ **查询改写**（让 LLM 先把问题扩充成多种问法）。这些在你本地都能做，先做第一个。

### 4.5 怎么知道你的 RAG "好不好"

写 10 个你已知答案的问题当**评测集**。改 ANY 参数前先跑一遍记分，改完再跑——没有评测集的调参都是掷骰子。这一个习惯，比多看十篇 RAG 教程值钱。

## 5 总表：每个工程动作 ↔ 它背后的原理

| 你在教程里写的 | 原理篇里对应的一句 |
|---|---|
| messages 数组每轮重发 | 模型无状态，上下文=唯一工作内存 |
| system prompt 放规则 | 训练格式让开头指令权重最高 |
| 4bit 量化模型 | 压缩浮点数低位的有效性，8B 进 12GB 显存 |
| tools 定义 + description | 训练出的"调工具习惯"，靠语义匹配触发 |
| tool_call_id 回传 | 服务端的调用结果对账协议 |
| agent 的 while 循环 | ReAct：把难题拆成每步稳赢的局部决策 |
| 工具报错回传 | 把环境反馈接进下一轮条件概率 |
| max_turns 上限 | 概率机器没有内驱停止 |
